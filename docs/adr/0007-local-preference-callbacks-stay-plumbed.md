# Favorites and visibleColumns keep their callback plumbing instead of a preferences store

An architecture review flagged the persistence path for the two values the table owns locally, `favoritePokemonIds` and `visibleColumns`, as a shallow five-hop callback chain: `TableScreen` calls `onFavoritesChange` / `onColumnsChange`, `PokedexApp.svelte` forwards it, `PokedexView`'s constructor forwards it again, and the lambdas in `main.ts` reach `PokedexPlugin.setFavorites` / `setVisibleColumns`, which assign onto `this.settings` and call `saveData`. The review proposed a local-preferences store (`get` / `set`, optionally `subscribe`) so a new locally-owned preference would need no new props through three layers.

On inspection the chain is plumbing, not a place a bug can hide, and a store would not be deeper than what it replaces:

- **The two "copies" do not drift.** `TableScreen` seeds `favoriteIds` and `visibleColumnKeys` once via `untrack`, and `settings.favoritePokemonIds` / `settings.visibleColumns` hold the other copy. But `setFavorites` and `setVisibleColumns` mutate the same `this.settings` object that `saveSettings()` remounts from (`PokedexView.mountApp` passes `this.getSettings()` into `PokedexApp`), so every remount re-seeds `TableScreen` with the latest value. The "never re-seeds" hazard in `src/view/CLAUDE.md` concerns live verification, not correctness.
- **Stale persisted values are harmless.** `TableScreen` filters `TOGGLEABLE_COLUMNS` through `visibleColumnKeys.has`, so an unknown column key is ignored, and a favorited id with no matching row is ignored too. There is no load-time validation or sanitizing for a store to absorb.
- **Deletion test.** The store would be an assignment plus `saveData`, about 15 lines, with no logic of its own: deleting it just moves one assignment back to its caller. That is a shallow module. The two forwarding hops (`PokedexApp`, `PokedexView`) are also shallow, but deleting them would not concentrate any complexity either; it would only change which prop carries the callback.
- **Two persistence paths are the point, not an accident.** `saveSettings()` remounts every open tab (right for dex range, Active Gen, sprite style); `setFavorites` / `setVisibleColumns` persist without a remount, because the table already updated locally and a remount would reset scroll, sort and filters. Only two values use the second path today.

**Decision:** leave the callbacks, `setFavorites` and `setVisibleColumns` as they are. Rejected alternatives: bundling the two callbacks and two `initialX` props into one object prop (saves a few props, adds no logic), and a full local-preferences store (shallow, see above).

**Reopen when** a third locally-owned persisted preference is added (last sort column or direction, last filters, last-open detail Pokemon), at which point the per-preference cost of three layers of props starts to outweigh a small bundling object, or when a real persistence bug is observed (favorites or columns lost across a remount or reopen). Don't re-flag the chain's length alone in a future review without one of those.
